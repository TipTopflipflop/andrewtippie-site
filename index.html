How I Think

The document below is the methodology I use to build AI systems. It's not theoretical — it produced a 900-line, build-ready specification for Leon (CBL) across 17 phases. v2.0 incorporates the patches that survived running the methodology against itself: structured FMEA, an anti-anchor baseline, per-stage instrumentation, and a counterfactual baseline stage that measures what the methodology actually added.

The Iterative Multi-Disciplinary Design Methodology

Version 2.0 — Updated 2026-05-15  ·  A reusable process for taking an idea to a fully-architected, build-ready specification

Known Limits (Read Before Using)

These are the structural weaknesses the consortium identified during the self-review. They are not fully fixed in v2.0. They are real and you should know about them.

  1. The single-generator problem. Every "discipline" in the consortium is simulated by one model. Agreement among simulated experts is coherence, not independence. The methodology produces internal consistency; it does not produce external validation.
  2. N=1 evidentiary base. The claim that this methodology produces better architectures rests on one application (CBL). There is no published counterfactual, no comparison to alternative methodologies, no tracked outcomes from real builds. Stage 11 begins to address this but does not resolve it.
  3. No cross-provider review. True independence would require at least one pass from a different model provider. Treat this as an external validation step if the project warrants it.
  4. Inside the generator's prior. The methodology cannot find architectures that lie outside what the generating model can imagine. Stage 2b partially compensates but does not eliminate the bound.
  5. Self-review is not validation. v2.0's patches were derived by the methodology applying itself to itself. That tells you the methodology is internally critique-able — not that the patches actually improve real-world output.

What v2.0 Changed

  • New Stage 0: Pre-Registration. Falsifiability criteria, project-refusal gate, and declared stage requirements written before the methodology begins.
  • New Stage 2b: Anti-Anchor Baseline. A second architecture from opposite first principles, carried in parallel until one is reasoned out.
  • Replaced freeform adversarial review with structured FMEA. Tabular, traceable, scored (Severity × Likelihood × Detectability = RPN).
  • Per-stage instrumentation. Novel claims, restatements, and drops tracked per stage. Novelty floor stops ceremonial stages.
  • Falsifier required per architectural decision. "We chose X because Y; Y would be wrong if Z." No falsifier, no commitment.
  • New Stage 11: Counterfactual Baseline. A one-pass design from the same generator produced at the end and compared.
  • Contrarian-first review. Each persona produces one explicit disagreement before any "consensus" is recorded.

The Core Insight

Most "design a system" conversations produce mediocre results because they take one pass. One model, one perspective, one shot — competent but generic, covers what's obvious, misses what isn't.

The methodology below produces better results because it explicitly simulates the multi-perspective review that real-world architecture goes through, compressed and accelerated. It works — to the extent it works — because:

  1. Different disciplines see different things. A neuroscientist notices missing memory consolidation. A hostage negotiator notices binary clarification. A jazz musician notices broken timing. None of these are reachable from a single-perspective pass.
  2. Constraints make architecture better. Forcing the system through ten lenses, the parts that survive all of them tend to be structurally sound.
  3. Iteration with instrumentation converges. Repeated review with fresh perspectives catches what prior passes missed. In v2.0, instrumented novelty per stage tells you when you've actually converged versus when you're running ritual.
  4. Trust architecture cannot be designed in one shot. Safety, scope, refusal, and trust require adversarial review. They emerge from disciplined challenge.
An important caveat: the methodology produces coherence. Coherence is not truth. Read the Known Limits above before treating any output as validated.

The Stages

The methodology now has eleven stages. Each requires multiple exchanges. Total: 40–60 substantive exchanges from idea to build-ready spec. Stages 0, 2b, and 11 are new. Stage 5 is replaced.

Stage 0 — Pre-Registration (NEW)

Commit to falsifiable criteria before applying the methodology. Write down what the project is trying to accomplish. Write down what "this methodology failed for this project" would look like — explicit, observable, dated conditions. Decide whether the project should be built at all. Declare which stages are required, which are conditional, which are optional. Set the novelty floor for Stage 9 convergence (typical: fewer than three genuinely new claims = below floor). Output: a pre-registration document, dated, confirmed by user — not revisable based on later results.

Stage 1 — Establish the Real Problem

Surface what the user actually wants to build. Take the description at face value briefly. Ask one or two clarifying questions. Restate in your own words and confirm. Ask what the tool does that existing tools don't, or what currently breaks about the workflow. Output: a clean problem statement everyone agrees on.

Stage 2 — Initial Architecture

Sketch the obvious solution before improving it. Propose what a competent engineer would build: technologies, components, data flow. Acknowledge limitations honestly. This is the baseline against which improvements are measured.

Stage 2b — Anti-Anchor Baseline (NEW)

Prevent the methodology from hill-climbing inside Stage 2's basin of attraction. Generate a second baseline from opposite first principles — if Stage 2 was centralized, make this decentralized; if stateful, stateless; if model-first, rule-first. The opposition must be architectural, not cosmetic. Carry both baselines through Stages 3–5. Drop one only when a review produces a defensible logged reason, or merge into a hybrid that explicitly inherits from each.

Stage 3 — First Improvement Pass: The Smarter Friend

Critique by a more experienced perspective, applied to both baselines. "If I handed this to a senior engineer, what would they say?" Generate concrete additions: specific named techniques, real algorithms, real APIs. Acknowledge tradeoffs.

Stage 4 — Multi-Team Review (3–5 Teams)

Review from professional perspectives directly relevant to the problem domain. Each team contributes 5–10 concrete improvements in their voice. Contrarian-first: each team must produce one explicit disagreement before any consensus is recorded — immediate agreement is mode collapse. Identify cross-team coherence points (note: coherence, not validation — see Known Limits). End each section with what the team is worried or enthusiastic about.

Stage 5 — Structured FMEA (REPLACES freeform adversarial review)

Enumerate failure modes in a tabular FMEA: Failure mode · Cause · Effect · Severity (1–5) · Likelihood (1–5) · Detectability (1–5, where 5 = hard to detect) · Risk Priority Number (S×L×D) · Mitigation · Mitigation type (design-out vs. policy-out). Items with RPN ≥ 50 require an explicit architectural mitigation, not a policy mitigation. Output: FMEA table with all rows traced to a mitigation in the spec.

Stage 6 — Toggle / Mode Architecture (if relevant)

If the system serves multiple user populations, design tiered access. Safest tier is default; highest tier is gated by something verifiable. Cryptographic gates beat trust-the-user. Structural separation between tiers, not policy separation.

Stage 7 — Visionary / Think Tank Review

Strategic and platform-level concerns the engineering review missed. Futurists, economists, product strategists, platform thinkers. Long-term position, network effects, emergent properties, moat. Apply novelty floor: if this stage produces fewer than three genuinely new claims, log that and reduce its weight rather than padding.

Stage 8 — Cross-Domain Expansion

3–5 disciplines unusual for this problem: neuroscientists, biologists, theoretical physicists, jazz musicians, liturgical scholars, hostage negotiators. Apply novelty floor — if a discipline genuinely adds nothing, say so. Do not pad with plausible-sounding contributions.

Stage 9 — Iterative Convergence (UPDATED)

Run review repeatedly with instrumentation until novelty drops below the pre-registered floor. Instrument each stage: count novel claims added, claims that are restatements, claims dropped under later review. Convergence = novelty below floor for two consecutive stages. Typical: 3–4 full review passes. Do not run extra passes for impressiveness.

Stage 10 — Build-Ready Translation

Translate architecture into a build plan a builder can execute. Produce a SPEC.md with: precedence rules, safety invariants (unoverridable), performance targets with variance/p99 bounds, build order with ship gates, deferred items, explicit refusals, versioned changelog. Falsifier requirement: every architectural decision must include a falsifier — "We chose X because Y. Y would be wrong if we observed Z." No falsifier, no commitment. Produce a BRIEF.md that bootstraps an AI builder, short and foolproof.

Stage 11 — Counterfactual Baseline (NEW)

Establish what the methodology actually added. Take only the Stage 1 problem statement. Generate a one-pass design from the same model — no iteration, no multi-discipline review, single response. Compare to the methodology's output. Document what the methodology added that one-pass missed. Document what one-pass got right that the methodology over-complicated. Log both for future calibration. Without this stage, you are claiming the methodology added value without measuring whether it did.

Patterns That Reliably Emerge

These showed up in CBL because they tend to show up in well-architected systems. Look for them, but don't force them.

  1. Layered Perception. Multiple input channels; prefer the most semantic. Visual as fallback, not primary.
  2. Two-Agent Planner/Executor. Strong model plans, cheap deterministic process executes, verifier catches failures.
  3. State as a Graph, Not a Blob. State-transition graphs preserve causal information; flat state loses it.
  4. Probabilistic Verification. Binary success/fail produces false confidence. Probabilistic with explicit uncertainty produces correct behavior under noise.
  5. Memory With Consolidation. Continuous systems degrade without periodic offline reorganization.
  6. Control Mechanisms From Physical Engineering. Rate limits, control rods, dampers, pressure-relief valves. 70+ years of cascading-effect prevention; most AI systems skip and pay later.
  7. Three-Tier Mode Architecture. Personal → Organizational → Research/Power-user. One product, three populations, appropriate safety per tier.
  8. Structural Separation, Not Policy. Type systems, cryptographic gates, architectural compartmentalization. Misuse impossible by design, not forbidden by rules.
  9. Constitutional Layer Distinct From Safety Invariants. Invariants enforced; constitutional principles consulted. Both necessary, different functions.
  10. Refusal as Feature. Public refusal logs, documented categories, refusal-with-explanation are trust-building.
  11. Forensic-Grade Audit. Hash-chained, third-party verifiable, immutable, exportable. Tamper-evident by design.
  12. Designed Pauses and Timing. Speed is not always the goal. Deliberate pauses signal thinking; timing matters as much as accuracy.
  13. Dev-Bypass Flags With Visible Banners. Build-time flag + git-diff visibility + runtime warning + UI banner. Cheap, prevents real embarrassment.
  14. Phase Gates With Concrete Ship Criteria. Explicit "this is done" criteria per phase. Don't advance past gates that don't pass.
  15. The Precedence Rule. Safety invariants > scope/permission gates > constitutional principles > performance targets > everything else. Holds across every application of this methodology to date.

Changelog

v2.0 — 2026-05-15. Self-applied consortium review identified six structural weaknesses in v1.0: single-generator coherence mistaken for validation, unfalsifiability, anchoring at Stage 2, no counterfactual baseline, no instrumentation, no project-refusal gate. Patches: added Stages 0, 2b, and 11; replaced freeform adversarial review with structured FMEA; added per-stage instrumentation and novelty floor; added per-decision falsifier requirement; added contrarian-first protocol; added explicit Known Limits section. Patches are derived from internal review only and have not yet been validated against real-world application.

v1.0 — original. Methodology that produced the CBL architecture. Ten stages, multi-disciplinary review, build-ready translation to SPEC.md + BRIEF.md.

v1.0 produced an unusually rigorous architecture for CBL. v2.0 incorporates the patches that survived running v1.0 on itself. Neither version has been validated against a counterfactual baseline or against an alternative methodology. What you have is a structured process that survives its own internal review, with documented limits. Treat the distinction between coherence and validation as load-bearing.
