How I Think

The Iterative Multi-Disciplinary Design Methodology

A reusable process for taking an idea to a fully-architected, build-ready specification

The Core Insight

Most "design a system" conversations produce mediocre results because they take one pass at it. One model, one perspective, one shot. The result is competent but generic — covers what's obvious, misses what isn't.

The methodology below produces dramatically better results because it explicitly simulates the multi-perspective review that real-world architecture goes through, but compressed and accelerated. It works because:

  1. Different disciplines see different things. A neuroscientist notices that a system has no equivalent of memory consolidation. A hostage negotiator notices that the clarification questions are too binary. A jazz musician notices that the timing is wrong. None of these are reachable from a single-perspective design pass.
  2. Constraints make architecture better. When you force the system through ten different lenses, the parts that survive all of them are structurally sound. The parts that don't survive get refined or removed.
  3. Iteration converges on truth. Running the same review process repeatedly with fresh eyes catches things prior passes missed. There's a natural convergence point past which further iteration produces noise rather than signal — usually around the third or fourth pass.
  4. A proper trust architecture cannot be designed in one shot. Safety, scope, refusal, and trust patterns require explicit adversarial review. They emerge from disciplined challenge, not from one-pass design.

The Stages

The methodology has approximately ten stages, each requiring multiple exchanges. Total interaction count for a complex system: 30–50 substantive exchanges from idea to build-ready spec. Do not rush through them.

Stage 1 — Establish the Real Problem

Surface what the user actually wants to build, beneath the surface description. Take the description at face value briefly, restate the problem back in your own words, and ask if that's right. Ask what the tool would do that existing tools don't, or what currently breaks about the workflow. Output: a clean problem statement everyone agrees on.

Stage 2 — Identify the Initial Architecture

Sketch the obvious solution before improving it. Propose what a competent engineer would build: name technologies, list components, describe data flow. Acknowledge limitations honestly. The first-draft architecture is the baseline against which improvements are measured.

Stage 3 — First Improvement Pass: The Smarter Friend

Have the architecture critiqued by a more experienced perspective. Frame it as: "If I handed this to a more senior engineer, what would they say?" Generate concrete additions with specific names (real algorithms, real APIs, real techniques) over generic advice. Acknowledge tradeoffs.

Stage 4 — Multi-Team Review (3–5 Teams)

Review from professional perspectives that map directly to the problem domain — for example, for a browser tool: Chromium engineers, ML researchers, accessibility engineers, enterprise architects, red team security. Each team contributes 5–10 concrete architectural improvements in their voice. Identify cross-team consensus points — where multiple teams independently arrive at the same conclusion, that's load-bearing architecture.

Stage 5 — Adversarial Review

Identify the dangerous failure modes before they ship. Bring in a red team explicitly: misuse, attack surfaces, ethical failures, legal exposure. Distinguish between threats that should be designed-out (architectural changes) and threats that should be policy (rules). Create the structural separation that prevents misuse — enforced by architecture, not trust.

Stage 6 — The Toggle / Mode Architecture

If the system serves multiple user populations, design the mode/tier architecture. Identify populations with different needs (consumer, enterprise, professional, researcher). Design tiers that escalate capability with proportional safety. The safest tier is the default; the highest tier is gated by something verifiable. Make the gate cryptographic where possible — verifiable beats "trust the user."

Stage 7 — Visionary / Think Tank Review

Catch strategic and platform-level concerns the engineering review missed. Bring in perspectives that look at the system as a whole: futurists, economists, product strategists, platform thinkers. Identify emergent properties — capabilities the system has when you combine its components that aren't obvious from any one component alone. Identify the moat.

Stage 8 — Cross-Domain Expansion

Add disciplines not previously consulted to surface what's still missing. Bring in 3–5 disciplines that wouldn't normally be consulted on this problem — neuroscientists, biologists, theoretical physicists, jazz musicians, liturgical scholars, hostage negotiators. The unusual perspectives often catch what the obvious perspectives missed.

Stage 9 — Iterative Convergence

Run the review process repeatedly until further iteration produces no new signal. After each pass, identify what was new vs. what was rediscovery. Track when the rate of new signal drops sharply — that's convergence. Typical convergence: 3–4 full review passes. Beyond convergence, additional passes produce variance, not improvement.

Stage 10 — Build-Ready Translation

Translate the architecture into a build plan that an engineer (human or AI) can execute. Produce a SPEC.md organized by section (~500–1000 lines for a complex system) including: precedence rules, safety invariants, performance targets, build order with ship gates per phase, deferred items, and explicit refusals. Produce a BRIEF.md that bootstraps an AI builder — short, foolproof, with the absolute floor encoded so it survives context loss.

Patterns That Reliably Emerge

These showed up in CBL because they show up in well-architected systems generally:

  • Layered Perception. Most systems perceive through one channel. Better systems perceive through multiple layers and prefer the most semantic one. Visual is fallback, not primary.
  • Two-Agent Planner/Executor. A strong model plans, a cheap deterministic process executes, a verifier catches failures. This pattern recurs across every kind of agent system because it's structurally correct.
  • State as a Graph, Not a Blob. Flat state representations lose causal information. State-transition graphs preserve it and enable reasoning about reversibility, causality, and consequence.
  • Probabilistic Verification. Binary success/fail produces false confidence. Probabilistic verification with explicit uncertainty handling produces correct behavior under noise.
  • Memory With Consolidation. Continuous AI systems that don't consolidate memory degrade over time. Add periodic offline reorganization and you get stable long-term performance.
  • Control Mechanisms Inspired by Physical Engineering. Rate limits, control rods, dampers, pressure-relief valves — physical engineering has 70+ years of cascading-effect prevention. AI systems usually skip this and pay for it later.
  • Three-Tier Mode Architecture. Personal (default, safe) → Organizational (managed, audited) → Research/Power-user (gated, capable). Lets one product serve three populations with appropriate safety per tier.
  • Structural Separation, Not Policy. Where misuse is possible, build the architecture so misuse is impossible without explicit unsafe action — not so misuse is forbidden by rules.
  • Refusal as Feature. What the system refuses to do is as important as what it does. Documented refusal categories and refusal-with-explanation are trust-building patterns.
  • Forensic-Grade Audit. Hash-chained, third-party verifiable, immutable, exportable. Audit logs that are tamper-evident by design.
  • Phase Gates With Concrete Ship Criteria. Each build phase has explicit "this is done" criteria. Don't advance past gates that don't pass.
  • The Precedence Rule. When decisions conflict: safety invariants > scope/permission gates > constitutional principles > performance targets > everything else.
This methodology produced an unusually rigorous architecture for CBL because it didn't take shortcuts. The same methodology will produce comparably rigorous architectures for other problems if applied with the same discipline.
